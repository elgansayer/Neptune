# Saturn and Power: source investigation and executable next experiments

Date: 30 October 2026. Owners: #478 and #509; execution index #477.
The [source registry](sources-2026-10-30.json) records 39 references, retrieval date,
revision where available, limitations and destination issues. `S01`–`S39` below
refer to those entries. This is an applied source investigation, not a claim of
new original-game execution, new extracted art, complete decompilation or parity.

## Decisions from this investigation

1. Validate one small original kernel routine before attempting a whole-game
   reconstruction. The new `tools/saturn_lab/probe_kernel.py` implements that first
   experiment with original-file and interpreter hashes, bounded execution,
   mutation controls and an explicit result. The original is on the VPS, which
   this chat cannot execute commands on; the real result remains pending.
2. Reuse the accepted Beetle bridge for reference behaviour. Evaluate Kronos's
   existing **raw texture export** first for a first art result, with Ymir as an
   additional tracing/comparison candidate. Do not restart emulator development.
3. Separate screenshot contact sheets, decoded textures, composed character
   frames and verified animation timelines. Each is a different output.
4. Identify Power's actual release/container before selecting code tools. Its
   GameMaker route has practical Linux CLI exporters; recover metadata alongside
   pictures so the work can feed a real mod format.
5. Advance code, graphics, audio and behaviour through bounded experiments with
   existing owners and shared budgets. No new scheduler or paid tooling is needed
   for the first slices identified here.

The nine named candidates are: `0600665C` register initialisation; `06006B38`
record activation; `0600940A` entry clearing/countdown; `0600942E` batch clearing;
`0600A3E0` position bounds; `0600A4B0` prioritised input-bit selection;
`0600B934` table-address arithmetic; and `0600A25E`/`0600A2D8` split-halfword
position accumulation. These descriptions come from the upstream C, not our own
verified disassembly. The input-bit routine is the narrowest useful first target.
Its proposed precedence is `0x4000 -> 3`, `0x2000 -> 2`, `0x8000 -> 1`,
`0x1000 -> 4`, otherwise zero. Direction names need caller evidence. [S02]

The upstream `disc.json` gives `BOMSS/0KRNL.BIN` length 786432 and SHA-1
`6fc53e5715d89cae7b4684bb3b65165ac1865736`. Our accepted USA summary gives the same
length and SHA-256 `20109f506afd076af8a8583121dbb5a4880e0a764ee8e004c17b0cb055c798a7`.
The new probe checks **both** identities; matching size alone is insufficient.

### Source-level traps found

- `decomp/check.py` can select zero functions with an unknown name and can run
  zero trials with a non-positive count. Its normal process success is therefore
  insufficient acceptance evidence without selection/count assertions.
- That checker maps `0x05D00000` as flat memory called VDP1. The candidate
  `0600665C` writes its cache-through alias `0x25D00000`, which is the VDP1
  **register** area, not texture VRAM (`0x05C00000`). Flat byte equality there
  does not validate register side effects. Use the pure input helper first.
- `CPU.call` uses the instance's cumulative step count. Create a fresh CPU for
  each case; do not let earlier cases consume a later case's instruction budget.
- The random differential checker shares the upstream interpreter. An agreement
  can share an interpreter error. Follow with a pinned original emulator trace.
  [S03, S07, S18; the upstream `hw.py` map also identifies the register range.]

`lab.sheet` reads `build/test/NAME/shot-*.png`; it does not inspect texture memory.
`compare.py` reports pixel mismatches as data and returns a report; callers must
assert completion and expected comparisons, not interpret an exit as parity.
Basic comparisons reject invincibility hooks and multitap but **do accept memory
writes**, despite older README wording. Record those writes explicitly.
Game-tick alignment helps with loading but cannot prove equal VBlank timing in
menus/round transitions where that tick stops. [S04, S05 and pinned compare.py]

The game configuration explicitly requests `SATURN_VDP1_GPL=ON`. The optional
renderer is therefore enabled in that configured build. Keep the research build
and its component notices separate from Neptune's Apache-2.0 engine; do not
describe the complete configured upstream binary as MIT-only. [S06, S08]

## EXP-SAT-CODE-001: runnable first function experiment

The probe is deliberately limited to `0600A4B0`, loaded at `06006000`, from the
accepted USA kernel. It checks 256 arguments spanning all sixteen selected-bit
combinations, four unrelated low-bit patterns and four upper-word patterns.
These are sampled 32-bit inputs, not a proof over all possible inputs. It rejects
unexpected writes/unmapped reads, exceptions, wrong results and more than 256
instructions per call. Reports include per-case results and their digest.

It loads only hash-verified `hw.py`, `sh2.py` and `sh2emu.py` from the pinned
dependency, without executing its package initializer. Third-party code is not
vendored. Run under the existing unprivileged research environment; source hashes
are not a substitute for that isolation. This CPU experiment needs neither a
compiler purchase nor a new emulator/BIOS installation.

After checking the existing private extraction, the host owner runs:

```sh
timeout 60s python3 tools/saturn_lab/probe_kernel.py \
  --kernel /PRIVATE-EXTRACTION/BOMSS/0KRNL.BIN \
  --saturn-recomp /PINNED-CHECKOUT/saturn-recomp \
  --report /PRIVATE-EVIDENCE/UNIQUE-code-001.json
```

Replace the placeholders with inspected paths; create the private evidence parent
first. The report must be new and is never overwritten. If the kernel is not yet
extracted, use the accepted disc tooling/owner workflow and verify its hash;
do not send the binary into this chat. The source checkout must be the pinned
dependency; the probe does not download tools or change source data.

After a passing result, independently observe that routine's calls/returns on
the original emulator, recording input registers, entry/return PCs and selected
results with code identity. Include simultaneous/opposite input bits and a
deliberate changed-return/precedence control. Publish the evidence and limitations
in a real research PR; leave #478/#483 open for the remaining functions and
whole-game validation. CPU-only results are not movement/fuse timings.

### A real spritesheet needs more than screenshots

The capture contract for #485/#487 should retain command identity and order,
texture address and size, pixel format, lookup/palette references, flips,
coordinates and colour/effect flags. VDP1 command source addresses use units of
eight bytes; the horizontal character dimension also uses eight-pixel units.
End-code handling differs from transparent pixels. Preserve these distinctions
and reject malformed command loops and out-of-range texture spans. [S14, S15]

VDP2 controls sprite interpretation/composition, including palette addresses,
sprite type, priority and colour calculation. Keep CRAM and relevant registers
with the texture snapshot. Export a lossless index/raw representation plus an
RGBA preview and explicit unresolved effects. VDP2 background extraction also
needs pattern names/attributes and arrangement, not just a screenshot. [S16]

Our proposed stages are: a verified raw texture; composed character frames with
anchors; deduplicated atlas with provenance; and an animation timeline observed
in unmodified gameplay. Deduplicate content by texture **and** palette/format,
keeping aliases. Changing palette can change a frame without changing texels.
Capture transitions over time because one VRAM snapshot cannot establish all
frames. Keep mesh/shadow/Gouraud states separate from a baked preview.

The firsthand Saturn ripper explicitly reports missing Normal-only Bomberman and
Tirra animations despite broad existing sheets. Seed those as coverage gaps in
#487/#515. Do not treat another collection's completeness or filenames as proof
of our supplied USA/JP content. [S31]

## Sound and movies

Upstream inventory config proposes a sound-driver span in PROGRAM.BIN at offset
`0x44`, length `0x63D4`, another in XBAND.DAT at `0x11868`, and a NetLink driver
file. These are concrete byte-comparison leads for #488, not proof all sound
resources share a format. Gemini's bank-memory work remains its own claim. [S06]

Start with driver identification, a sequence/tone relationship and one triggered
sample. kingshriek's tools are driver-specific and warn about false positives;
VGMTrans documents Sega sequence/instrument formats. Test both against identified
structures before generalising. Preserve driver, tone bank, sequence, DSP and
mixer provenance; a recognisable MIDI/WAV is not original-system equivalence.
[S33, S35]

`ssfplay_tools` offers bounded headless SSF rendering, register capture and
triggered-sample dumps. It derives from Mednafen and only observes exercised
sounds. Its sample WAV defaults add silence, so separate exact PCM from audition
files and record the padding. Its Ymir slot tool is documented in that project's
local checkout context; verify the dependency before assuming it exists in
upstream Ymir. Record pitch, sample format, loop endpoints/mode and mix state.
[S17, S34]

Saturn `.CPK` files identified as Sega FILM should go through a verified FILM
decoder, such as FFmpeg's `segafilm` path, not a CRI archive extractor selected by
extension. Preserve packet offsets, timestamps and decoded frame/audio hashes.
For CDDA retain track/index/pregap accounting and compare sample alignment before
calling regional audio different. Compression/conversion success does not prove
the source belongs to the claimed release. [S36; accepted #473 inventory]

## Gameplay hypotheses worth testing first

The Master-mode TAS authors report: subpixel accumulation can continue when
holding direction against a wall; explosion collision is smaller than the visible
flame; a kicked bomb's fuse continues; picking up a bomb resets its timer and
airborne time behaves differently. These are **firsthand hypotheses**, specific
to that run/build, not accepted Neptune constants. Direct page access was
restricted, so retain the retrieved submission text as a lead and obtain the
actual input movie/version before replay adoption. [S32]

For #493/#492, test wall-blocked and free motion with the same input duration,
separate integer/subpixel state, and vary speed upgrades. Measure bomb states
placed/held/airborne/rolling/landed independently, including transitions one tick
before expiry. Sweep collision boundaries against active flame state, not visible
pixels. Repeat in Normal, Master and Battle; do not copy one mode's values into
all profiles. Deliberate one-tick and one-subpixel mutations must fail comparisons.

Menu navigation, field/frame boundaries, game ticks and audio sample time are
distinct clocks. Store each available clock and an alignment record. Model
workers inspect compact traces while scripts perform sweeps. Extend to co-op
friendly fire, death/revival, exits, shared camera and checkpoint state only with
equivalent verified initial conditions. Existing #395–#399 retain broader coverage.

## Power Bomberman: a practical extraction path

The developer post still advertises 0.7.8c dated 1 March 2026, platform clients and
a matching optional server. Pin the downloaded bytes, included manual, executable
and container; displayed version alone cannot exclude a hotfix. The changelog
link could not be opened during this pass, so no newly verified changelog claims
are made. No client/server was downloaded or run here. [S29]

A mod author's Jyamarui instructions identify an actual older `data.win`/UTMT
workflow and show that replacing a character also touches embedded textures and
menu icons. This is a useful resource dependency example, not proof the current
release has the same IDs or that its whole code is VM bytecode. [S30]

The inspected UTMT CLI source supports `info`, `dump --sprites`, `--textures` and
`--code`. The documented exporters also cover assembly, collision masks, fonts,
audio, tilesets and room previews. The room-PNG script is Windows-GUI-only;
do not let a Linux worker repeatedly call it as if headless support existed.
Start with the actual chosen CLI's `--help`, `info` and one resource in a fresh
directory. Preserve sprite origins, extents, padding, frame ordering, texture-page
relationships and masks through a small metadata exporter where needed.
[S25–S27]

VM decompilation and native YYC analysis are different branches. Underanalyzer is
a GML VM library, not a solution to arbitrary native binaries. Keep assembly,
inferred GML and runtime-observed behaviour separately. Identify the real object
events/rules corresponding to one power-up, then exercise that item in an owned
local match. Recover simulation-affecting parameters separately from graphics.
Power's networking experiments must use our local server, not public matchmaking.
[S28; #499/#503/#506]

For the community engine, these findings favour data-only character packs with
explicit anchors/animation metadata, maps with separate collision/spawn/gimmick
data, and power-ups composed of versioned engine capabilities. Do not expose
imported executable scripts as downloadable mods. Author one original fixture
through that API while reference work proceeds. Extraction dependencies must not
block multiplayer/bots or creator-authored solo/co-op campaigns.

## Ghidra, agents and tool installation

The Saturn Ghidra loader's own documentation says ISO import loads only the
first file. It also lists missing mirror handling and limitations in old save
state formats. Import 0KRNL and later overlays explicitly with region, load range
and lifetime; verify mappings and relocated pointers instead of expecting one
ISO import to recover the entire game. Use built-in SH-2 support, then identify
known libraries before counting routines as game-specific code. [S22]

Ghidra's supported headless import and scripts are the baseline. GhidraMCP now
documents a headless PyGhidra path, but its inspected setup targets Ghidra 12.1.4,
Java 21 and Python 3.10–3.13, while current Ghidra main documentation calls for
JDK 25. #518/#508 must pin and smoke-test a compatible combination; combining
every latest component is not a reproducible recipe. Persist projects and bounded
reports, restrict the adapter to the authorised local workspace, and test failure
handling before routing shared agents through it. [S23, S24, S39]

Other leads are lower priority: `sonsegajp/SaturnRecomp` explicitly says its
current public play path is interpreted and the full AOT emitter is absent.
The Resident Evil reconstruction offers different-game tooling examples, not
Bomberman format evidence. Record these in the registry without turning their
project names into completion claims. [S37, S38]

## Verification performed and remaining limits

The local input-tooling suite contains 60 passing tests, including ten new probe
contract tests. Wrong-sized/changed originals, modified interpreter code, empty
coverage, wrong precedence, unexpected writes, invalid instruction evidence and
report overwrite are rejected. A real load of the pinned Python interpreter was
smoke-tested with hand-authored SH-2 instructions: ordinary return, a return-delay
slot, and a non-returning loop. Those are synthetic tool checks only.

The first smoke test exposed a missing `hw.py` dependency; the loader was corrected
to verify and load all three files. No test uses original game bytes, no new
sprite or sound was extracted, and no new original routine was verified in this
chat. A qualifying first result still requires the real VPS experiment and its
evidence PR so the existing email watch can assess it.
